# 사람이 읽기 편한 백로그 작성 가이드

Task Mecca backlog는 **사람이 빠르게 판단하는 문서**이면서 Agent가 실행·검증·복구에 사용하는 durable record다.
따라서 첫 화면은 짧고 명확하게, 상세 기록은 손실 없이 보존한다.

## 0. 사용자 언어와 인지 부하

백로그는 사용자가 태스크를 이해하기 위해 내부 Agent의 표현을 자기 언어로 다시 번역해야 하는 문서가 아니어야 한다.
제목, 핵심 요약, 작업 정의·요건 정의, 상태·결과·후속 설명은 사용자가 실제 대화에서 쓰는 언어와 용어 감각을 기준으로
자연스럽게 작성한다.

정확한 기술 식별자나 전문용어는 원문을 유지할 수 있다. 다만 영문 용어가 남더라도 문장의 수식 관계와 어순은 사용자 언어에
맞게 다시 구성한다. 내부 framework 문서의 축약된 영어 표현을 그대로 옮기는 것은 피한다. 이를 위해 언어별 용어표나
치환 규칙을 만들 필요는 없으며, 각 Agent가 문맥과 사용자가 이미 사용하는 표현을 바탕으로 의미를 보존해 재서술한다.

### 내부 구현 표현을 사용자 문장으로 옮길 때

Agent 내부 작업 메모나 Worker 보고를 그대로 백로그 문장으로 복사하지 않는다. 구현에서 쓰는 개념과 식별자는 정확히
보존하되, **사용자가 읽는 문장은 업무 문서로 자연스럽게 다시 서술**한다.

- API 경로, 필드명, 상태값, 저장되는 lineage 값처럼 **시스템이 실제로 사용하는 식별자**는 `code` 표기로 원문을 유지한다.
- `canonical clone`, `exact plan`, `legacy projection`, `five-state diff`, `fail-closed`처럼 Agent가 사고 과정에서 압축해 쓰는
  **개념 설명**은 그대로 노출하지 말고 사용자 언어로 의미를 풀어쓴다.
- 필요한 전문용어는 처음 한 번 원어를 괄호로 병기할 수 있지만, 이후 문장은 사용자 언어가 문법과 수식 관계를 지배한다.
- 영어 명사구에 한국어 조사만 붙인 문장, 여러 명사를 연속으로 쌓은 표현, 동작을 과도하게 명사화한 표현을 피한다.
  가능하면 **누가/무엇이 무엇을 한다**가 드러나는 동사 중심 문장으로 쓴다.
- 한 문장에 구현 조건·예외·결과를 과도하게 몰아넣지 않는다. 의미 단위가 다르면 문장을 나눈다.
- Worker의 DONE/BLOCKED 보고는 사실 근거로 사용하되, Controller가 백로그 `결과`·`검증`·`핵심 요약`에 반영할 때
  사용자-facing 문장으로 다시 작성한다.

예를 들어 다음은 내부 구현 표현이 과도하게 노출된 문장이다.

```text
backend 계약과 회귀 테스트를 구현했다. canonical clone은 exact plan을 보존하고
legacy projection·rerun·Method 전환은 각각 별도 lineage와 fail-closed 진단을 제공한다.
```

사람이 읽는 백로그에서는 같은 의미를 다음처럼 표현한다.

```text
백엔드 처리 규약과 회귀 테스트를 구현했다. 일반 설계 복제는 당시 확정된 실행계획을 그대로 보존한다.
레거시 실험 복제, 재실행, Method 전환은 각각의 생성 이력을 남기며,
안전하게 처리할 수 없는 경우에는 작업을 중단하고 그 이유를 명확히 안내한다.
```

또한 다음처럼 **실제 식별자는 유지하고 주변 설명만 자연스럽게** 쓴다.

- 피함: `field_id 기반 five-state diff를 반환한다.`
- 권장: ``field_id``를 기준으로 입력 차이를 비교하고 각 항목을 유지·추가·삭제·규칙 변경·자동 전환 불가 중 하나로 구분한다.
- 피함: `legacy projection은 allowlist contract로 처리한다.`
- 권장: 레거시 실험에서는 명시적인 허용 목록(allowlist)에 포함된 입력만 가져오도록 처리 규칙을 분리한다.
- 피함: `incompatible 입력은 fail-closed한다.`
- 권장: 자동 전환할 수 없는 입력은 임의로 변환하지 않고, 필요한 사용자 입력이나 중단 이유를 명확히 제시한다.

이 예시는 고정 번역표가 아니다. 같은 영문 용어라도 코드 식별자인지, 제품 개념인지, 사용자가 이미 쓰는 전문용어인지에 따라
문맥에 맞게 판단한다.


## 1. 정보 계층

### 1단계 — 핵심 요약

`## 핵심 요약`은 기본 화면에 노출되는 사람용 projection이다.

- `목적`: 왜 필요한 작업인지 한 문장
- `핵심 변경`: 무엇을 바꾸는지 또는 실제 무엇이 바뀌었는지
- `상태·결과`: 현재 단계·남은 일 또는 완료 결과·검증 판정
- `확인·후속`: 차단, 실패, 승인 요청, 중요한 미검증, 후속 작업이 있을 때만

기본 3~5개 짧은 항목을 가이드로 삼되, 단순 작업에 빈 설명을 억지로 늘리지 않는다.
정확한 수치·허용 오차·식별자·제외 조건·실행 로그는 요약으로 대체하지 않고 상세에 보존한다.

### 2단계 — 현재 맥락과 메타정보

`## 핵심 요약` 바로 아래에는 사용자가 현재 작업의 위치와 흐름을 먼저 파악할 수 있도록 다음 정보를 둔다.

- 관련 작업
- 운영·실행 근거
- Lifecycle

이 정보는 작업 본문보다 먼저 배치하되, 세부 운영 기록이 핵심 요약을 압도하지 않도록 간결한 현재 상태를 먼저 보여준다.

### 3단계 — 항목별 상세

그 다음에 실제 작업 내용을 다음 축으로 구분한다.

- 배경 및 문제
- 작업 정의 / 요구사항
- 작업 범위와 제약
- 완료 기준
- 진행 상황·작업 결과
- 검증 상세

각 상세 섹션의 접기/펼치기는 **의미 있는 섹션 요약이 있을 때만** 사용한다.

긴 내용이어서 상세 전체를 읽기 전에 핵심 판단이 가능해야 하는 경우, 해당 섹션의 첫 부분에 선택적으로 다음 형식을 사용한다.

```markdown
> 요약: 이 섹션 전체를 읽지 않아도 핵심 판단이 가능하도록 전체 의미를 한두 문장으로 정리한다.
```

- 이 요약은 본문 첫 문장을 단순히 줄인 문장이 아니라 **섹션 전체를 관통하는 의미 요약**이어야 한다.
- 요약이 있으면 Web UI는 요약을 항상 표시하고 상세 본문만 접거나 펼친다.
- 요약이 없으면 Web UI는 접기/펼치기 요소를 만들지 않고 본문을 바로 보여준다.
- 짧거나 이미 충분히 명확한 섹션에는 요약을 억지로 추가하지 않는다.
- 글자 수 임계값으로 요약 필요 여부를 판정하지 않는다. 작성 Agent가 내용의 성격과 사용자의 인지 부담을 보고 판단한다.
- 기존 백로그에 이 표식이 없어도 별도 변환하지 않는다. 해당 본문을 그대로 보여준다.

### 4단계 — 정확한 근거

검증 상세와 운영 정보에서 테스트 결과, 로그, 커밋, 실험 식별자, Lifecycle, Runtime/Dispatch 근거 등
정확한 원문으로 이어져야 한다.

## 2. 출처

외부 이슈에서 시작된 작업은 사용자가 백로그만 보아도 원천을 바로 확인할 수 있게 `출처`를 남긴다.

- 권장: `[Linear · ENG-123](https://...)`
- 권장: `[GitHub · owner/repo#84](https://...)`
- 직접 대화에서 시작되어 별도 외부 원천이 없으면 `-`

URL이 있으면 Markdown 링크 자체가 원본으로 이동하는 수단이며, Task Mecca Web에서도 같은 출처를 클릭 가능한 링크로 보여준다.
출처는 작업의 출처 추적 정보이지 현재 실행 계약을 대신하지 않는다.

## 3. 제목

제목은 추상적인 내부 명사 조합보다 **업무 대상 + 바뀌는 내용/결과**를 드러낸다.

- 피함: `현행 결과 기준선 및 재현 비교 계약 확정`
- 권장: `실험 결과 재현 여부를 자동으로 비교하는 기준 마련`

필요한 전문용어는 유지하되, 제목만 읽고 작업 의미를 추정하기 어려운 내부 운영 용어를 앞세우지 않는다.

## 4. 상태별 요약 갱신

### 등록(todo)

- 목적
- 예정 핵심 변경
- 완료 기준의 의미
- 이미 알려진 제약/승인 필요사항

예:

```markdown
## 핵심 요약
- 목적: 같은 조건으로 다시 실행했을 때 기존 결과가 재현되는지 자동으로 확인한다.
- 핵심 변경: Studio 실행과 직접 실행의 결정 경로·성과를 비교하는 기준과 테스트를 추가한다.
- 상태·결과: 등록 완료. 비교 기준 구현과 재현 테스트가 남아 있다.
- 확인·후속: 대형 결과 파일 저장 최적화는 별도 작업으로 유지한다.
```

### 진행 중(doing)

과거 계획보다 **현재 단계와 남은 일**을 우선한다.

```markdown
## 핵심 요약
- 목적: 동일 조건 재실행의 결과 재현 여부를 자동 검증한다.
- 핵심 변경: 비교 기준과 테스트 harness 구현은 완료했고 실제 Studio/직접 실행 비교를 검증 중이다.
- 상태·결과: 주요 비교 테스트는 통과했다. 전체 회귀 검증과 결과 기록이 남아 있다.
- 확인·후속: 전체 코드 검사의 기존 오류는 이번 작업 범위 밖인지 최종 검증 기록에 명시한다.
```

### 사용자/외부 차단(hold)

차단 사유와 사용자가 해야 할 일을 요약에 숨기지 않는다.

```markdown
## 핵심 요약
- 목적: 배포 환경에서 새 인증 흐름을 적용한다.
- 핵심 변경: 코드 변경은 준비됐지만 운영 계정 승인 후에만 실제 검증할 수 있다.
- 상태·결과: 사용자 승인을 기다리는 중이라 검증이 중단됐다.
- 확인·후속: 운영 계정 접근 승인이 필요하다. 승인되면 배포 검증부터 재개한다.
```

### 완료(done)

계획 문구를 그대로 남기지 않고 **실제 변경과 검증 결과**를 우선한다.

```markdown
## 핵심 요약
- 목적: 동일 조건 재실행의 결과 재현 여부를 자동 검증한다.
- 핵심 변경: Studio 실행과 직접 실행을 비교하는 기준과 자동 테스트를 구현했다.
- 상태·결과: 재현 비교는 통과했다. 전체 코드 검사의 기존 오류는 이번 통과 범위에 포함하지 않았다.
- 확인·후속: 대형 결과 파일 저장 용량 축소는 별도 후속 작업에서 처리한다.
```

## 5. B-413 표현 예시

### 개선 전

```text
현행 결과 기준선 및 재현 비교 계약 확정
```

제목만으로 실제 사용 목적이 드러나지 않고, 긴 기술 설명과 운영 메타데이터를 읽어야 결과를 이해할 수 있다.

### 개선 후

**실험 결과 재현 여부를 자동으로 비교하는 기준 마련**

- 목적: 같은 조건으로 다시 실행했을 때 기존 결과가 동일하게 재현되는지 확인한다.
- 결과: Studio 실행과 직접 실행을 비교하는 기준과 자동 테스트를 구현했다.
- 검증: 재현 비교는 통과했다. 전체 코드 검사의 기존 오류는 이번 작업의 통과 범위에 포함하지 않는다.
- 후속: 대형 결과 파일 저장 용량 축소는 별도 작업으로 처리한다.

정확한 비교 대상, 연속형 값 허용 오차, 제외 항목, 테스트 명령과 결과는 각각 작업 범위·완료 기준·검증 상세에서 확인한다.

## 6. 역할별 책임

- Root: 사람이 이해할 수 있는 제목과 최초 목적/예정 변경을 정한다.
- Registrar: Root의 의미를 바꾸지 않고 `## 핵심 요약`과 canonical contract를 등록한다.
- Worker: 완료/차단 보고에 실제 변경, 검증, 남은 일, 중요한 예외를 명시한다.
- Controller: state transition 때 `상태·결과`와 `확인·후속`을 최신 사실로 갱신한다.
  완료 시 필요하면 `핵심 변경`을 계획 표현에서 실제 결과 표현으로 갱신한다.
- 어떤 역할도 핵심 요약을 이유로 원래 contract, 수용 기준, 제약, 검증 근거를 삭제하거나 축약하지 않는다.

## 7. 일관성 규칙

- 요약과 상세의 성공/실패/미검증 판정이 다르면 안 된다.
- `hold(user)`, 차단, 실패, 승인 요청, 중요한 미검증은 요약에 반드시 드러낸다.
- 완료 후 과거 진행 메모를 현재 상태처럼 노출하지 않는다.
- 관련 작업은 ID만 나열하지 않고 관계 의미를 상세에 기록한다.
- legacy backlog는 일괄 변환하지 않는다. Web UI는 기존 contract/result/attention 정보로 fallback 요약을 제공한다.
